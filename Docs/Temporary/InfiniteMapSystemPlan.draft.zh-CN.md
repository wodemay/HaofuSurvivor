# 无限地图系统策划草案

> 状态：讨论中。本文不代表已实现内容，不生成 Docs Viewer 数据，不提交 GitHub。

## 目标

地图不是一张固定场景，而是围绕玩家持续展开的无限世界。

- 世界按区块生成，玩家前进时加载附近区块。
- 远离玩家的区块卸载 GameObject，只保留数据。
- 返回旧区域时，根据原始数据恢复区块、掉落物和事件，不重新随机。
- 地图事件可以跨越很长距离持续存在，例如区域击杀、宝箱、精英、祭坛和奖励点。
- 远处的重要事件与物品通过屏幕边缘箭头指引。
- 继续游戏后，世界布局、玩家位置、事件进度和长期存在的物品应保持一致。

## 模块边界

本计划只负责地图本体。道具、地图事件和箭头指引不并入地图核心，而是独立订阅地图提供的数据与生命周期通知。

- 地图系统：地表、区块坐标、阻挡物、可通行网格、敌人导航数据、区块加载与卸载。
- 道具系统：道具生成、拾取、持久化状态和奖励逻辑；只使用地图提供的世界坐标与区块状态。
- 地图事件系统：事件实例、触发条件、进度、奖励和完成状态；只使用地图提供的区域与加载通知。
- 世界指引系统：箭头目标筛选、优先级和 UI 表现；通过事件系统与道具系统提供的目标查询工作。

地图核心可以发布 `ChunkLoaded`、`ChunkUnloaded`、`WorldPositionChanged` 等通知，但不负责解释道具、事件或箭头的业务含义。

## 基本原则

### 数据与表现分离

每个区块同时存在两层概念：

- `ChunkData`：记录坐标、生成结果、实体状态、事件状态和修改记录。
- `ChunkView`：包含地面、装饰、碰撞、事件触发器和可见物品的 GameObject。

卸载区块时只回收 `ChunkView`；`ChunkData` 继续留在运行时世界数据或存档中。重新靠近时，系统由相同的 `ChunkData` 重建 `ChunkView`。

因此“地图卸载”只是不显示、不占用场景对象，不会让玩家已经看见、拾取、完成或留下的内容被重置。

### 确定性生成与状态增量

新对局由系统内部创建一个 `WorldSeed`。同一 Seed 加上区块坐标，始终得到相同的基础地图内容。Seed 不向玩家显示、不提供输入入口，也不作为可选玩法；它只随对局快照保存，用于继续游戏时重建同一张世界。

- 未被玩家影响的区块无需完整存档，随时可由 Seed 重新生成。
- 已被影响的内容只保存增量状态，例如宝箱已开启、物品已拾取、事件完成、地图障碍已破坏。
- 这样无限地图不会随着玩家探索范围线性保存所有视觉数据。

### Unity Tilemap 的定位

Unity 内置的 2D `Grid`、`Tilemap` 和 Tile Palette 是网格地图的编辑与渲染工具，不是自动生成无限世界的完整方案。它适合承担 `ChunkView` 中的地表、装饰和 Tilemap Collider 表现，但不负责世界 Seed、区块数据、卸载恢复、事件状态或存档。

本项目推荐让 `WorldMapSystem` 先生成或读取 `ChunkData`，再由地图表现层把该数据批量写入少量共享 Tilemap。地图实体、事件和长期物品仍作为独立 Prefab 挂到场景根节点。这样既利用 Tilemap 的绘制、碰撞和合批能力，也不会把业务状态锁死在 Unity 场景对象里。

### 推荐的区块视觉结构

在 Tilemap 作为表现层的前提下，具体采用“每区块独立 Grid/Tilemap + 独立 Prefab 内容”的混合方案。区块卸载时整体禁用或回收对应 Grid，不在一张无限变大的 Tilemap 上反复清理区域。

- `Grid`：区块局部网格，位置由区块坐标换算得到。
- `GroundTilemap`：地表和基础纹理，使用 `MapBackground`。
- `DecorationTilemap`：规则化装饰，使用 `MapDecoration`。
- `ObstacleVisualTilemap`：阻挡物外观，可使用 `MapDecoration` 或隐藏 Renderer。
- `ObstacleColliderTilemap`：只负责移动与投射物碰撞，可挂 `TilemapCollider2D` 和 `CompositeCollider2D`，不承担排序层。
- `ContentRoot`：事件、地标、长期物品和其他 Prefab 内容。

区块表现对象由对象池复用。第一版只加载玩家周围有限数量的 `MapChunkView`，不创建无限数量的 Tilemap。

纯 Prefab 拼接的美术自由度高，但对象数量、接缝管理、碰撞和卸载成本都高；纯 Tilemap 的网格性能最好，但复杂地标和事件区域受限。混合方案把地表与规则阻挡交给 Tilemap，把复杂内容交给 Prefab，最符合当前项目。

## 世界坐标与区块

世界使用现有 2D XY 平面。每个区块用整数坐标标识：`(ChunkX, ChunkY)`。

- 每个区块对应一个固定大小的正方形世界区域。
- 玩家世界坐标可转换为所在区块坐标。
- 区块坐标也是所有地图实体与事件的稳定归属位置。
- 每个可持久化实体都需要全局唯一 ID；推荐由世界 Seed、区块坐标、生成序号组合得到，而不是依赖 Unity Instance ID。

初始建议把区块边长设为可配置值，而不在代码中写死。最终数值需要结合角色移动速度、相机视野和单区块美术密度决定。

## 区块生命周期

地图系统只维护玩家附近的活动区块集合。

1. 玩家进入或靠近尚未加载的区块范围。
2. 系统读取已有 `ChunkData`；没有时按 Seed 生成基础数据。
3. 从对象池获取或创建 `ChunkView`，生成地表、装饰、碰撞和当前仍有效的实体。
4. 玩家远离后，区块进入卸载候选。
5. 超过卸载范围时，回收区块下所有表现对象，保留 `ChunkData`。

加载范围与卸载范围必须不同：卸载范围略大，形成缓冲区，避免玩家在边界来回移动时反复加载和回收同一批对象。

## 地图内容

一个区块的基础生成结果可分为四类。

### 地表

地表定义视觉主题、底图变化和可通行区域。第一版可以使用少量可拼接地图块；后续再扩展地形噪声、道路、房间、生态区和主题切换。

### 装饰与阻挡物

装饰物不影响移动；阻挡物拥有碰撞并改变可通行区域。阻挡物不能完全随机散布，必须由可配置图形模板和连通性规则共同生成。

#### 阻挡物配置

每种阻挡物图形应作为独立配置项参与生成，而不是把坐标直接写死在代码里。配置至少包含：

- 图形占用的网格掩码，以及允许的旋转/镜像方式。
- 生成权重、最小间距、与区块边界的最小距离。
- 允许出现的地图主题、区块阶段和距离出生点的范围。
- 是否阻挡角色移动、是否阻挡投射物、是否可破坏。
- 对应的表现 Prefab 或 Tilemap 图形引用。

#### 道路不封死的生成规则

区块生成不能采用“随机放置后祈祷可通行”的方式。推荐流程如下：

1. 先根据 Seed 和区块坐标确定区块边界入口，并与相邻区块共享边界规则，保证两边入口对齐。
2. 先生成一条或多条受保护的主通路，连接出生点、区块入口和必要出口；主通路区域禁止放置阻挡物。
3. 在剩余区域中按配置权重尝试放置图形模板，放置后立即检查可通行网格。
4. 使用 Flood Fill 或 A* 检查出生点与所有必要入口是否连通，并检查可通行面积下限。
5. 检查失败时回滚本次图形，改用其他模板或降低密度；达到重试上限后使用保底开放布局，不能生成不可玩的区块。

区块边界的入口规则必须是确定性的。否则单独生成相邻区块时，左区块可能认为边界开放，右区块却认为边界封闭，玩家会在接缝处遇到墙。

敌人当前是直线追踪，因此阻挡物一旦阻挡角色移动，就必须同步加入绕行或寻路能力；不能只给地图加碰撞体而保留原有追击逻辑。

#### 敌人寻路

类幸存者玩法通常同时存在大量敌人，它们共享同一个主要目标——玩家。因此当前方案采用“2D NavMesh + 按需 A* + 路径缓存”：导航图连续表达可行走区域，敌人不通过方格直角移动，也不在每个固定帧重复寻路。

- 地图生成后输出可通行网格，阻挡物所在格为不可通行。
- 根据当前已加载区块的地面与移动阻挡层，节流构建运行期 2D NavMesh。
- 每个可通行格保存朝向玩家的下一步方向；敌人只需采样自身所在格的方向。
- 敌人仍由 `EnemySystem` 统一固定帧调度，并使用 `Rigidbody2D.MovePosition` 移动。
- 玩家跨越网格/区块、地图阻挡变化或敌人长时间没有位移时，重新计算对应导航区域。
- 生成导航网格时按敌人碰撞半径膨胀阻挡区域，避免敌人贴墙或穿过过窄通道。
- A* 没有可达路径或敌人卡住时，清理该敌人的路径缓存并等待下一次按需重算，不能持续向墙体施加移动。

导航数据只解决“如何绕过地图阻挡物”；敌人之间的分离、拥挤和碰撞仍由独立的局部避让逻辑处理，不能把大量敌人互相挤压的问题交给全局寻路。

#### 阻挡投射物

移动阻挡与投射物阻挡应拆成两条规则，不要只依赖一个碰撞层：

- 角色碰撞体决定玩家和敌人能否穿过。
- 投射物阻挡体决定子弹是否被拦截。
- 同一阻挡物可以只挡角色、只挡子弹，或同时阻挡两者。
- 投射物命中阻挡物后按攻击参数处理：通常返回对象池；具有穿透能力的投射物再决定是否消耗穿透次数。

这样后续可以配置草丛、墙体、能挡子弹但可穿过的能量屏障等不同规则，而不需要在每种攻击 Executor 里写地图特判。

### 长期存在物品

宝箱、材料、地图掉落、可拾取道具等使用持久化实体记录。

- 未拾取：重新加载时恢复。
- 已拾取：只保留状态，不再生成表现。
- 被移动或被改变：保存当前状态与位置。

战斗中的经验球、普通投射物等短生命周期对象仍由现有战斗系统管理；是否需要跨区块或跨存档保存，应与地图长期物品分开决定。

### 地图事件

事件是附着在世界坐标或区域上的持久化玩法实例，而不是仅存在于当前场景的 Trigger。

事件数据至少需要保存：

- 事件 ID、类型、所属区块、世界位置和作用半径。
- 状态：未激活、进行中、已完成、已领取、失效。
- 进度：例如区域内击杀数量、剩余敌人、倒计时或阶段。
- 奖励状态，防止卸载或重复加载后重复领取。

首批可以只实现一种区域击杀事件：玩家进入范围后，要求在范围内击杀指定数量敌人，完成后生成奖励。事件逻辑、奖励和视觉配置必须拆开，后续才能扩展精英、守卫、护送和祭坛。

## 远距离指引

地图指引只关心“值得玩家前往的目标”，而不是所有实体。

- 目标来源：进行中的地图事件、已完成待领取的奖励、稀有掉落、特殊交互物。
- 目标优先级：待领取奖励 > 进行中事件 > 稀有物品 > 普通物品。
- 目标在相机内时不显示箭头；在相机外时投影到屏幕边缘。
- 同一方向的低优先级目标可聚合，避免箭头淹没画面。

箭头属于 UI。依据现有 UI 边界，后续由管理员创建 UI Prefab 与 Bind，代码只负责提供目标数据和接入显示逻辑。

## QFramework 归属

业务状态不放在场景 MonoBehaviour 中。

- `WorldMapModel`：WorldSeed、生成版本、区块数据、阻挡网格和导航缓存。
- `WorldMapSystem`：区块坐标计算、确定性生成、区块加载决策、存档序列化入口。
- `MapChunkSystem`：管理活动 `ChunkView`、对象池和表现回收。
- `MapNavMeshSystem`：生成运行期 2D NavMesh、按需计算并缓存连续路径，处理阻挡变化。
- `ItemSystem`、`MapEventSystem`、`WorldGuideSystem`：独立模块，只通过地图 Query、Event 和世界坐标接入，不属于地图核心。
- Commands：开始/恢复对局、区块状态变更、事件推进、物品状态变更。
- Queries：活动区块、实体数据、事件、指引目标。
- Events：区块加载/卸载、事件状态变更、奖励生成与领取。

地图的帧更新仍由 `GameLoopSystem` 调度，只在 `RunPhase.Active` 中检查玩家跨区块、区块加载和导航数据。暂停、升级选择、死亡和结算期间不推进地图生成或导航。

## 场景与渲染约束

场景只保留稳定根节点，动态区块和实体挂到对应根节点下。区块加载不得修改场景资产本身。

渲染遵循现有九层排序规则：

- 地表：`MapBackground`
- 地图装饰：`MapDecoration`
- 地面危险区：`GroundEffect`
- 地图可拾取物：`Pickup`
- 敌人、玩家、投射物、战斗特效和世界 UI：继续使用各自既有层

管理员拥有场景层级、Tilemap、地图 Prefab 与 UI 结构；实现阶段需要这些资源时，先由管理员创建，再接入代码。

## 存档边界

继续游戏的总快照需要恢复以下状态；其中只有前两项属于地图核心，其余由对应系统负责：

- 世界 Seed 与生成版本。
- 已修改区块的增量数据。
- 玩家位置与当前区块由 Run/Player 系统保存。
- 长期存在物品的状态与位置由 Item 系统保存。
- 地图事件状态、进度和奖励领取状态由 MapEvent 系统保存。

不保存可由确定性生成还原的基础地表，也不保存已被回收的 Unity 表现对象。存档需要设置版本号，后续修改生成算法时以生成版本区分，避免旧存档被新算法错误解释。

## 性能原则

- 不为无限世界创建无限 GameObject；仅维护加载范围内的表现。
- 区块、装饰、可拾取物、事件表现都应复用对象池。
- 不让每个地图对象各自 `Update`；统一由地图 System 根据区块集合批量调度。
- 加载与卸载应分帧预算处理，避免玩家高速移动时单帧创建大量对象。
- 导航场只在玩家网格、区块或阻挡数据发生变化时重建，不为每只敌人单独计算完整路径。
- 地图数据只保存差异状态；序列化频率沿用后续统一的存档节流策略。

## 第一阶段临时视觉原型

在完整无限地图之前，先使用一个开放的网格平面验证基础玩法。

- 场景中保留 `WorldRoot/MapRoot/Grid/GroundTilemap` 层级。
- 使用单一地面 Tile 填充一个足够大的矩形范围，排序层使用 `MapBackground`。
- 临时地图不生成阻挡物，因此不添加地图碰撞；玩家、敌人和投射物可以在开放平面上运行。
- 暂不接入 WorldSeed、区块数据、地图事件、长期物品、寻路和区块卸载。
- 地面范围通过配置的宽度和高度控制，不把“无限”伪装成无边界；后续完整系统接入时，将 GroundTilemap 的填充来源替换为 `ChunkData`。
- 该原型只验证地图视觉、玩家移动、摄像机跟随、敌人生成和攻击表现，不承担最终地图玩法。

临时方案仍保留未来的根节点命名和渲染层约束，避免后续从场景结构重新迁移。

## 讨论清单

以下内容确认后，才进入具体任务拆解与实现：

1. 地图视觉方案暂定为“区块 Tilemap + 独立 Prefab 内容”；需要确认 Tile 资源风格与第一版区块层数。
2. 区块尺寸、可视加载半径、卸载半径与相机关系。
3. 世界 Seed 只作为内部存档字段；需要确认新对局是否始终自动随机生成。
4. 出生区是否安全，以及安全区的尺寸与规则。
5. 阻挡物的第一版是否使用网格占用图，以及敌人采用简单绕行还是完整寻路。
6. 阻挡物模板是否由 ScriptableObject 配置图形掩码、权重、旋转和碰撞规则。
7. 敌人导航使用 2D NavMesh 和按需 A*；特殊敌人后续可在同一导航接口上增加独立移动策略。
8. 第一批地图主题、资源点和事件类型。
9. 长期物品与战斗临时掉落物的具体边界。
10. 指引箭头的目标上限、优先级、显示形式和是否允许玩家关闭。
11. 继续游戏是否必须恢复所有世界事件和长期物品，还是只恢复当前附近区域。
12. 地图扩展是否需要预留生物群系、关卡边界、Boss 区域或传送点。

## 当前结论

先用开放 Tilemap 验证基础玩法，再确定世界数据结构、阻挡规则和生成算法。临时地面只是表现原型，不应提前承担无限地图的持久化职责。
