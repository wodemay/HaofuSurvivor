# Repository Guidelines

## Project Structure & Module Organization

This directory is the Unity project's `Assets/` root. Put game code in `Scripts/`: gameplay belongs in `Scripts/Game/` and UI panels in `Scripts/UI/`. Scene assets are in `Scenes/`; art content is in `Art/`; render and Unity asset settings are in `Settings/`. `QFramework/` and `QFrameworkData/` contain the installed framework and its generated configuration; do not edit framework sources unless explicitly upgrading it.

Gameplay is organized around QFramework. Keep Unity-facing components and panels as controllers/views; express state in Models, domain behavior in Systems, mutations in Commands, read-only calculations in Queries, and cross-module updates as typed Events. Register application services through an `Architecture` rather than introducing unmanaged global state.

## Build, Test, and Development Commands

Open the Unity project root (the parent of `Assets/`) with the version recorded in `ProjectSettings/ProjectVersion.txt`. Use the Unity Editor to open `Scenes/SampleScene.unity` and enter Play mode for local verification. There is currently no committed CLI build or automated test suite; add Unity Test Framework tests before claiming automated coverage.

## Coding Style & Naming Conventions

Write C# with tabs, four-space visual width, braces on separate lines, and PascalCase for types, methods, public fields, and serialized fields. Use camelCase for parameters and local variables. Keep the `HaoFuSurvivor` namespace for project code. Name UI panels `UI<Name>Panel` and retain QFramework's paired partial files: hand-written behavior goes in `Name.cs`; generated bindings remain in `Name.Designer.cs` and must not be hand-edited.

Always unregister QFramework event subscriptions with the owning GameObject lifecycle, for example `.UnRegisterWhenGameObjectDestroyed(gameObject)`.

## Testing Guidelines

Place new Unity Test Framework tests under `Tests/` with `Editor/` or `PlayMode/` subfolders. Name test fixtures after the subject and tests as `Method_Condition_ExpectedResult`. Cover Commands, Queries, and Systems without scene dependencies where possible; use Play Mode tests for Unity integration.

## Commit & Pull Request Guidelines

No commit history exists yet. Use imperative, scoped messages such as `feat(ui): add pause panel` or `fix(player): stop movement on death`. Keep each commit focused. Pull requests should state the behavioral change, list affected scenes/assets, link the issue when available, and include screenshots or a short capture for visible UI or gameplay changes.

## Persistent Project Context

`AGENTS.md` is the repository's durable handoff document. After every agent-performed operation that changes code, assets, scenes, configuration, architecture decisions, validation status, or known issues, update this file in the same task. Record only material facts: what changed, why, affected paths, verification performed, and unresolved follow-up. Do not overwrite existing history; append a dated entry under **Change Log**. Keep entries concise enough to scan in one pass.

Before every agent run or task action in this repository, read this entire `AGENTS.md` file first. Treat it as mandatory execution context, not optional reference material.

After every code change, perform a focused code review before validation, commit, push, or handoff. Review changed paths for compilation errors, QFramework boundary violations, lifecycle and pooling defects, null references, and unintended UI/prefab modifications; fix all findings before proceeding.

Write all project documentation in the project-root `Docs/` directory, never under `Assets/Docs/`.

- Combat baseline: Player and Enemy use the same `AttackSystem`, `AttackCatalog`, `AttackConfig`, runtime registration commands, executor registry, CombatEntity faction identity, and generic DamageSystem entry point. `EnemyConfig.AttackIds` supplies an enemy's current attacks; a future player skill/attack module will register its selected attack IDs through the identical flow.
- Attack extension contract: `Resources/Configs/Combat/AttackCatalog.asset` owns all attack definitions. `AttackConfig.ExecutorId` selects a registered `IAttackExecutor`; no AttackType enum, target-faction field, or central attack-type branch exists. Standard attacks derive the opposing target faction from the runtime owner: Player attacks Enemy and Enemy attacks Player. ID 1001 uses executor `collision` and retains its configured damage/cooldown. Add projectile, special, and player capabilities as new executors and registration triggers.
- Projectile attack contract: attack ID 1002 uses executor `projectile` and `ProjectileAttackParameter_Projectile.asset`, which references user-created `Art/Prefabs/Attack/Bullet.prefab`. `ProjectileAttackTrigger` gets the nearest opposing CombatEntity through `FindClosestCombatTargetQuery`; `ProjectileFactory` pools bullet instances under a runtime-only `ProjectileContainer`. The parameter asset supplies immutable base speed, lifetime, range, and pool capacity; future upgrades must apply runtime modifiers by attack ID instead of mutating assets.
- Skill-group contract: `CharacterConfig.SkillGroupId` resolves through `SkillGroupCatalog` to `SkillGroupConfig`, which provides starting weapon IDs, skill IDs, and one dodge ID. `WeaponConfig` is a static Weapon container template with `InitialAttackIds`, level rules, and upgrade eligibility; EnemyConfig continues to use AttackIds directly. `PlayerLoadoutSystem` creates one `WeaponRuntimeData` per player weapon and owns weapon upgrade, Attack replacement, direct replacement, and reset. Upgrades never mutate ScriptableObject assets.
- Weapon evolution contract: `WeaponEvolutionCatalog.asset` maps a source Weapon ID and required level to a target Weapon ID. Evolution retains the original WeaponRuntime slot ID, removes its old attack triggers, sets the target weapon to level 1, and registers its initial attack contents. `EvolveWeaponCommand` rejects targets unless `MaxLevel = 1` and `CanUpgrade = false`, so evolved weapons cannot re-enter the upgrade pool. The current path evolves Weapon 1 at level 5 into Weapon 2, which uses Attack 1003 and is level-1 non-upgradeable.
- Collision attack flow: EnemyFactory gives EnemyRoot CombatEntity faction identity, a Kinematic Rigidbody2D, and executor-defined trigger bridges. `CollisionAttackTrigger` resolves another CombatEntity's faction and sends generic register/try/unregister Commands; AttackSystem owns cooldown and invokes executor behavior. The current collision executor applies enemy timeline damage scaling before generic DamageSystem reaches PlayerSystem and the health bar. Pool release unregisters runtime state.
- Damage invulnerability baseline: PlayerStatModel exposes `DamageInvulnerabilityDuration`; PlayerModel tracks remaining time. The default duration is deliberately `0`, so current damage behavior is unchanged. Future upgrade logic may raise this stat by a small amount; PlayerSystem then ignores damage while the remaining time is positive.
- Enemy-health contract: `EnemyConfig.BaseHealth` is static base health. `EnemyFactory` registers each active EnemyRoot with `EnemyHealthSystem`, which applies the current `RunTimerModel.EnemyHealthMultiplier`, publishes damage/death events, and releases dead roots through `EnemySystem` back into the existing per-ID pool. All current enemy configurations use base health `20`; the survivor's projectile attack deals `10`, so a newly spawned opening-stage enemy dies in two hits before timeline health scaling.
- Experience-drop baseline: `EnemyConfig.ExperienceDrop` directly references `ExperienceDrop_Standard` and reserves `DropTableId` at 0. `EnemyDiedEvent` carries the immutable drop config and death position before EnemyRoot pooling; `ExperienceSystem` pools `ExperienceOrb` instances under the user-created `ExperienceDropContainer`. A drop captures once inside `PlayerStatModel.ExperienceAbsorbRadius`, then permanently tracks the player with acceleration and capped speed from the player's absorb attributes until collected; all motion uses `RunTimerModel.DeltaTime` and resets at run start/exit.
- Level-up baseline: `ExperienceSystem` ends at `PlayerLevelUpEvent`; it has no dependency on weapon upgrades, level-up UI, or RunPhase. `LevelUpSystem` owns a resettable queue of level-selection requests, current weapon-option query, selection confirmation, and `RunPhase.LevelUpSelection` entry/exit. `UILevelUpPanel` reads LevelUp queries and sends its confirmation Command. This initial slice offers only existing upgradeable Weapons; adding new Weapons, Skills, dodge upgrades, selection weights, and drop tables remains future work.
