# Repository Guidelines

## Project Structure & Module Organization

This directory is the Unity project's `Assets/` root. Put game code in `Scripts/`: gameplay belongs in `Scripts/Game/` and UI panels in `Scripts/UI/`. Scene assets are in `Scenes/`; art content is in `Art/`; render and Unity asset settings are in `Settings/`. `QFramework/` and `QFrameworkData/` contain the installed framework and its generated configuration; do not edit framework sources unless explicitly upgrading it.

Gameplay is organized around QFramework. Keep Unity-facing components and panels as controllers/views; express state in Models, domain behavior in Systems, mutations in Commands, read-only calculations in Queries, and cross-module updates as typed Events. Register application services through an `Architecture` rather than introducing unmanaged global state.

## Build, Test, and Development Commands

Open the Unity project root (the parent of `Assets/`) with the version recorded in `ProjectSettings/ProjectVersion.txt`. Use the Unity Editor to open `Scenes/SampleScene.unity` and enter Play mode for local verification. There is currently no committed CLI build or automated test suite; add Unity Test Framework tests before claiming automated coverage.

## Coding Style & Naming Conventions

Write C# with tabs, four-space visual width, braces on separate lines, and PascalCase for types, methods, public fields, and serialized fields. Use camelCase for parameters and local variables. Keep the `HaoFuSurvivor` namespace for project code. Name UI panels `UI<Name>Panel` and retain QFramework's paired partial files: hand-written behavior goes in `Name.cs`; generated bindings remain in `Name.Designer.cs` and must not be hand-edited.

Always unregister QFramework event subscriptions with the owning GameObject lifecycle, for example `.UnRegisterWhenGameObjectDestroyed(gameObject)`.

## Testing Guidelines

Place new Unity Test Framework tests under `Tests/` with `Editor/` or `PlayMode/` subfolders. Name test fixtures after the subject and tests as `Method_Condition_ExpectedResult`. Cover Commands, Queries, and Systems without scene dependencies where possible; use Play Mode tests for Unity integration.

## Commit & Pull Request Guidelines

No commit history exists yet. Use imperative, scoped messages such as `feat(ui): add pause panel` or `fix(player): stop movement on death`. Keep each commit focused. Pull requests should state the behavioral change, list affected scenes/assets, link the issue when available, and include screenshots or a short capture for visible UI or gameplay changes.

## Persistent Project Context

`AGENTS.md` is the repository's durable handoff document. After every agent-performed operation that changes code, assets, scenes, configuration, architecture decisions, validation status, or known issues, update this file in the same task. Record only material facts: what changed, why, affected paths, verification performed, and unresolved follow-up. Do not overwrite existing history; append a dated entry under **Change Log**. Keep entries concise enough to scan in one pass.

- Design baseline: `Docs/GameArchitecture.md` and `Docs/GameArchitecture.zh-CN.md` define the planned QFramework modules for the 2D survivor game. Existing gameplay code is disposable and must not constrain the new architecture.
- Gameplay baseline: the first implemented slice is the QFramework player-control foundation. `GameStart` initializes `GameArchitecture` and opens the character-selection flow; `PlayerController` is a non-UI `Rigidbody2D` bridge that must be attached to the future player GameObject. Its current desktop adapter reads legacy `Horizontal`/`Vertical` axes; touch input waits for user-created controls.
- Camera baseline: `PlayerSpawnSystem` binds the selected player's transform to `CameraFollow` on the `MainCamera`-tagged camera after a successful spawn. `CameraFollow` is currently declared beside the already-imported `GameStart` type, tracks XY in `LateUpdate`, and preserves the camera's initial Z position; no scene or UI object was changed.
- Startup flow: `GameStart` initializes ResKit and `GameArchitecture`, then opens `UICharacterSelectPanel` through UIKit using its configured asset bundle. A confirmed choice persists the ID and dispatches `StartRunCommand`; the run does not start before confirmation.
- Run timer design: `RunTimelineConfig` at `Resources/Configs/RunTimeline.asset` defines ordered time-point events. `RunTimerSystem` advances only in `RunPhase.Active`, publishes elapsed time and one typed event per reached configuration stage, and exposes current enemy health/damage/move-speed/spawn-rate multipliers through `GetRunTimerStateQuery`. `UIGameHUDPanel` displays elapsed time; future enemy, spawn, and event modules must subscribe to `RunTimelineStageReachedEvent` or query this state.
- Character selection baseline: `CharacterConfig` ScriptableObject assets under `Resources/Configs/Characters/` provide the roles with numeric IDs 1 (survivor), 2 (vanguard), and 3 (scout). `CharacterCatalog` is the QFramework Utility that loads and orders these assets; `CharacterSelectionModel` stores only the selected integer ID, and `CharacterSelectionStorage` persists it with `PlayerPrefs`.
- `CharacterConfig.Id` and `CharacterConfig.SkillId` are directly serialized integer fields. Skill ID 0 means no skill group is designed yet; no skill system, asset, or loading logic has been created.
- All `CharacterConfig` columns use direct serialized names without `m` prefixes: `Id`, `DisplayName`, `SkillDescription`, `SkillId`, `Icon`, `PlayerPrefab`, `SortOrder`, `MaxHealth`, `MoveSpeed`, and `AttackPower`.
- Character load contract: every `CharacterConfig` has a `PlayerPrefab` reference. The referenced gameplay prefab must contain `PlayerController` (which requires `Rigidbody2D`); `PlayerSpawnSystem` instantiates it at the origin after selection confirmation, then starts the run. Current mappings are survivor → `Square.prefab`, vanguard → `Triangle.prefab`, and scout → `Circle.prefab`.
- Temporary survivor spawn asset: `Character_Survivor` references `Art/Prefabs/Square.prefab`. Its root has `PlayerController` and a Kinematic `Rigidbody2D` with zero gravity; it is a temporary gameplay placeholder, not a final character prefab.
- Player-root contract: `Resources/Configs/PlayerRoot.asset` binds `Art/Prefabs/PlayerRoot.prefab` and `HealthBarCanvas.prefab`. `PlayerSpawnSystem` creates this root, ensures its movement components, parents each selected `CharacterConfig.PlayerPrefab` under `CharacterRoot`, and parents the health-bar canvas under `HealthBarAnchor`. The root prefab must retain both child names.
- Health-bar runtime contract: `PlayerHealthBarView` is added to each spawned health-bar canvas, reads the root player's QFramework health models, and refreshes its Slider on `PlayerDamagedEvent`. The user owns the canvas UI hierarchy and Slider binding.
- Enemy-root contract: `Resources/Configs/EnemyRoot.asset` binds `Art/Prefabs/EnemyRoot.prefab`. `EnemyFactory` creates this root per spawn, then parents the selected `EnemyConfig.Prefab` under `CharacterRoot`; the root prefab must retain that child name. `AttackRoot`, `EffectRoot`, `HurtBox`, and `DropRoot` are reserved for subsequent enemy systems.
- Enemy hierarchy and pooling: `Scenes/MainScene.unity` contains the active `EnemyContainer` root. EnemyRoot instances are parented there; `EnemyFactory` maintains a separate FIFO pool per enemy configuration ID, and `EnemySystem.Reset` returns active roots to that pool instead of destroying them.
- Enemy attack baseline: `EnemyConfig.AttackIds` is the ordered list of static attack IDs. `EnemyAttackCatalog` loads attack definitions from `Resources/Configs/Enemies/EnemyAttackCatalog.asset`; ID 1001 is the current Contact attack, with damage and cooldown configured in `EnemyAttack_Contact.asset`. Projectile and Special enum values are reserved but not implemented.
- Contact attack flow: EnemyFactory gives EnemyRoot a Kinematic Rigidbody2D and configures `EnemyContactAttack` for supported attack IDs. The bridge observes PlayerRoot/HurtBox trigger overlap and dispatches Commands to EnemyAttackSystem. The system owns cooldown/damage, applies the current run enemy-damage multiplier, calls DamageSystem, and therefore publishes the existing player health event for the health bar. Pool release unregisters attack runtime state.
- UI item implementation note: `UICharacterSelectItem` is an independent `MonoBehaviour` in `Scripts/UI/UICharacterSelectItem.cs`. It resolves the user-created item child nodes through `Transform.Find`; the panel owns only template cloning and selection flow.
- `UICharacterSelectItem` child paths: `Image_Select` and `Image_Icon` are direct children; `Text_Name` and `Text_Skill` are under the template's intermediate `GameObject` child and must be resolved as `GameObject/Text_Name` and `GameObject/Text_Skill`.
- `Scenes/TestUIPanels/TestUICharacterSelectPanel.unity` contains the UI root and `UICharacterSelectPanel`, but no `GameStart`. Run it additively after a boot scene, or add the existing `GameStart` component before using it as a standalone test scene; otherwise `GameArchitecture` is not initialized.
- Validation baseline: no committed automated tests or build scripts exist. The Git repository uses `main` and has an initial project commit.
